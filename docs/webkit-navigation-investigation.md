# WebKit 导航超时调查记录

更新日期：2026-11-03。**根因尚未确认，本文不是修复说明。**

## 问题与范围

`apps/web/tests/navigation-performance.test.ts` 中的
`SSR list and visited query variants return offline without another read`
偶发在点击文章后等待“固定正文”可见时超时，原断言期限为 5 秒。
[主分支失败记录](https://github.com/oliverran/fin_hot/actions/runs/41618589510)
保留了原始失败；[PR #3](https://github.com/oliverran/fin_hot/pull/3) 修复的搜索测试竞态是另一件事。

调查使用本地模拟接口和虚构文章，不连接真实采集、模型服务或用户数据。
测试环境为 GitHub Actions 的 Linux WebKit、Playwright 1.61.1，页面视口为 390×844。
这些结果尚未证明真实 iPhone Safari 存在同样的停顿。

## 已取得的证据

- [正文已出现但断言仍超时](https://github.com/oliverran/fin_hot/actions/runs/41630069837)：
  正文在断言开始后 454ms 进入 DOM，详情响应耗时 38ms；原断言仍在 5 秒超时。
  失败快照没有待处理的 React 工作。这排除了“正文始终没有渲染”作为该次失败的解释。
- [浏览器回调进入前发生延迟](https://github.com/oliverran/fin_hot/actions/runs/41634577964)：
  一个断言命令在 +480ms 发出，目标回调直到 +5,233ms 才进入，随后选择器和断言工作仅耗时 3ms。
  Node 心跳正常。长延迟不在这个回调内部，但单凭该记录不能区分浏览器调度与其他进程工作。
- [Timeline 捕获长 Paint 区间](https://github.com/oliverran/fin_hot/actions/runs/41641127803)：
  原生页面过渡就绪后出现 4,297ms 的全视口 Paint 记录，与断言命令延迟重叠；
  断言在 4,913ms 勉强通过，数据响应仅 29ms。
  Paint 记录的是经过时间，可能包含原生等待或进程未获调度，不能直接当作 CPU 绘制耗时。

这些记录来自不同样本，不应拼成同一次执行的时间线。

## 一次阴影对照实验

[对照 CI](https://github.com/oliverran/fin_hot/actions/runs/41642870240)
使用诊断提交 [589f5084](https://github.com/oliverran/fin_hot/commit/589f5084a0d4f3babd5c93318a05ed45d4e91ddb)。
每组各运行一次冷启动完整网页测试；两组都插入相同位置的诊断样式，仅前进过渡的
`::view-transition-new(root)` 阴影不同：原阴影与 `none`。
原生过渡、变换、时长、背景滤镜、返回过渡阴影、并发、模拟数据和原断言均保留。

- **原阴影组：**网页测试 61/62 通过，正文断言在 5,005ms 超时。
  正文已于 +645ms 进入 DOM，但一个耗时 4,585ms 的断言命令在期限之后才返回匹配成功。
  Timeline 中有 4,575ms 的 Paint 区间；后端测试与站点冒烟检查因网页失败未运行。
- **去掉前进阴影组：**网页 62/62、后端 991/991、站点冒烟检查通过。
  正文断言耗时 535ms，但此前点击文章耗时 4,366ms。
  返回列表后的首次“筛选”点击耗时 4,889ms，并与 4,694ms 的 Paint 区间重叠。
- “筛选”稳定性探针直接测到第二个动画帧回调延迟 **4,750ms**。
  两次矩形一致，读取矩形均耗时 0–1ms，之后的可见性与可用性检查立即完成。
  测量期间 Node 心跳正常；该次等待耗时集中在动画帧回调交付，而非已执行的矩形读取或状态检查。
- 两组类型检查与构建通过，独立的 Docker 检查也通过；整个工作流仍为失败，因为原阴影组复现了超时。

去掉前进阴影后，多秒延迟仍出现在流程的其他阶段。这一对样本**不能证明去掉阴影导致延迟转移，
不能认定阴影是根因，也不能证明问题已修复**。两组使用不同 CI 运行器，返回阴影未移除；
最初文章点击的长动作检查没有内部阶段探针，其具体阻塞位置仍未知。

## 保留方式与后续判断

[PR #4](https://github.com/oliverran/fin_hot/pull/4) 的历史诊断提交与 CI 链接保留了调查过程。
最终改动只保留本文；普通工作流和回归测试恢复为主分支版本，不保留依赖源码补丁、
私有 Playwright 桥接、阴影覆盖或常驻协议采集。原断言不放宽，测试不跳过。
原始协议产物设置了 7 天保留期，可能在之后失效，本文保存关键测量与限制。

现有证据支持“长原生 Paint 区间伴随目标回调或动画帧延迟”，尚未确定 CPU 绘制、
原生等待或进程调度中的哪一项负责。后续实验应能区分这些解释，并单独评估实验干预；
不能用重复重跑直到变绿、增加超时或移除阴影作为已验证的修复。
